# How Founder Repo OS Works

Founder Repo OS is built around a simple operating sequence: understand the repository, prepare the changes, and keep the merge decision with the repository owner.

## 1. Start from repository context

The customer describes the repository, team workflow, AI tools, and relevant operating needs. This produces a repository-specific setup plan rather than a generic one-size-fits-all template.

## 2. Select an authorized repository

The customer chooses the GitHub repository that is covered by the purchased scope. A repository connection alone does not change files.

## 3. Inspect the proposed setup

Founder Repo OS prepares the proposed files, operating rules, and governance structure for review. The customer sees the full diff before a repository write is requested.

## 4. Review a Draft Pull Request

When the customer explicitly confirms the plan, the intended workflow creates a dedicated branch and a Draft Pull Request. The owner can inspect the diff, request changes, or close the Pull Request without merging.

## 5. Decide whether to merge

The customer retains the merge decision. Founder Repo OS does not describe an automatic merge, deployment, or production release as part of the setup workflow.

## Maintained operating foundation

Founder Repo OS is offered as a maintained operating foundation. During an active subscription, relevant product updates may cover governance rules, AI-agent boundaries, review or release workflows, and compatibility with the supported Founder Repo OS operating model.

This does not promise a fixed update cadence, universal compatibility, security outcomes, or automatic remediation.
